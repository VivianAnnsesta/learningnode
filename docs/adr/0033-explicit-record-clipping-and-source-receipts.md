# ADR 0033: Explicit record clipping and fixed source snapshots

- Status: Accepted
- Date: 2026-11-09

## Context

Personal records already own immutable revisions, retained source snapshots and explicit creation/revision commands. Public teaching-source retrieval belongs to learning sessions; it must not be reused through a fabricated session for independent clipping. A user-declared external URL is not evidence that the server retrieved its text. Browser extension access must not bypass the Electron local-API authentication boundary.

## Decision

1. Provide in-app public HTML clipping and user-pasted text through a new read-only `POST /api/knowledge-points/clip-preview`. The response contains a fixed plain-text preview, ordered fragments with UTF-16 positions and hashes, acquisition mode/time, requested/final URL when applicable, extraction version and visible limitations. It creates no database row, learning event, AI call, relation or empty record. HTML is never executed; images, scripts, authenticated pages and PDF retrieval are outside this HTML/text contract and are not claimed as captured.

2. The user selects one or more preview fragments, then explicitly inserts text and its pending source together into the existing record draft. This operation preserves title, kind, aliases, assigned date, domain, source classification and existing sources. It uses the existing textarea position/newline rules. A safe undo restores only this insertion and removes only its newly added pending source; later body/source edits, base changes or saving invalidate undo. Previewing or rereading alone never changes the draft or saves it.

3. Each preview is one immutable capture. Its `snapshotKey` identifies all source metadata, capture time, extraction limits, text and fragment identities. The random `receiptId` only authorizes access to this process-local pending capture and is never persisted as source authority. Receipts have an absolute bounded lifetime and a bounded shared store. Reads/saves do not renew them; eviction, expiry or process restart returns HTTP 410 and preserves the draft. Rereading creates a new capture with a newly displayed time. The user explicitly adopts a replacement source after comparing it; existing body text is preserved for merging and is not silently reinserted or replaced.

4. Preview, creation and revision routes use the same Node-process store under a versioned symbol on `node:process`, including production standalone/Electron execution. It is not a module-local Map, database body table or second editable knowledge authority. Capacity supports the existing maximum number of source inputs. Cache tests alone do not prove cross-route deployment; real Next and packaged preview→create→revise evidence is required.

5. New source input is only `{kind:"clip", snapshotKey, receiptId, fragmentIds}`. The unique existing writer obtains the original metadata/text from the server store, verifies the full identity and ordered selected fragments, then persists a versioned `kind:"clip"` source snapshot inside `KnowledgePointRevision.sourcesJson`. The snapshot retains selected exact text/positions/hashes, whole-preview fingerprint, mode, URLs, capture time, extraction version and limitations. Client `obtained:true`, body, hash or metadata is never sufficient authority. No Prisma schema, migration, backfill or new record writer is needed.

6. Preserve the existing creation input hash, including raw source inputs, and `record-save:<requestId digest>` ledger. Check a successful prior before resolving a receipt, so replaying the same frozen command can find the existing record after expiry/restart. A new capture/selection changes the command input; it cannot reuse an old request ID to bypass its hash conflict. For clip-bearing creations return the existing ledger's saved revision identity and whether the command was reused, so current content is not mistaken for the original saved revision after later edits. No receipt, fresh capture time or new source replaces that original revision on retry.

7. When a clip-bearing create's outcome is unknown, retain its exact payload/request ID and provide explicit retry/result checking before accepting a replacement capture as a new save command. Replaying the old payload uses the original POST and prior check; a 410 received before any prior exists permits rereading. A preview error does not erase body or other fields. Revision continues to use its existing `expectedRevisionId` CAS, without a new generic revision ledger; 409 preserves pending clips and manual merging. Receipts are not consumed by failed saves. Source omission, retained indexes and exact old snapshots continue to preserve historical/raw sources, including unknown legacy forms.

8. Display current, pending and historical clip sources as readable fixed text cards. Public HTML is labelled as server-retrieved text with content unverified; pasted text is labelled as user-provided and not fetched from its declared URL. Manual provided time is not a webpage retrieval time. Unknown legacy sources retain their raw-reading fallback. Captured links still pass the explicit HTTPS guard before rendering. A clip is not a record backlink, semantic relation, AI acceptance, new record category or mastery fact; existing record references and saved-view source categories keep their meaning.

9. A dedicated server-only public HTML transport validates every URL and redirect, rejects credentials/control characters and nonpublic or mixed DNS answers, and pins the actual TLS connection to an approved address. It preserves the original hostname/Host/SNI and default CA/hostname verification, disables pooling/environment proxies, checks the connected peer and forwards no browser or local API credentials. The entire operation has one absolute deadline covering DNS, TLS, headers and body. Late DNS completion cannot start a request after cancellation; OS resolver work is not falsely described as cancelled. Streams are bounded and destroyed on failure; excess bytes, non-HTML media, unsupported content encoding and incomplete responses fail visibly instead of silently succeeding with truncated network data. Text extraction is bounded separately and discloses its preview truncation/heuristic limitations.

10. Keep existing teaching retrieval behavior unchanged. Its precheck followed by global fetch, per-hop deadline and extraction heuristics are not evidence for the new transport's connection pinning or whole-operation limits. New transport policies and failure paths need deterministic boundary tests, actual public HTTPS retrieval evidence when available, and caller cancellation cleanup. All API access retains the current Electron startup token, localhost Host/Origin, random port and 127.0.0.1 binding.

## Consequences

Clipping becomes an independent authoring workflow with useful offline source history after saving. Unstored captures are deliberately temporary; expired or changed content must be reread and explicitly adopted. A server fetch proves acquisition only, and a user selection proves intent only. Automated tests, retrieved text and successful packaging do not establish source correctness, teaching quality or distribution readiness.
